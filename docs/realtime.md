# リアルタイム同期の設計 — 通信とサーバー（#15）

オンライン対戦で「手番の進行が全員の画面にすぐ反映される」ことを、どう実現するかを決める。
ルールそのものは `docs/spec.md`、ゲームバランスの検討は `docs/design-notes.md` にある。
このドキュメントはその外側——**誰が状態を持ち、どう配り、切れたらどうするか**——だけを扱う。

ルールの細部が変わってもこの層は変えなくてよい形にしてある。
やり取りするのは「ルームの状態がこうなった」という事実だけで、
レーンが何本か・目標値がいくつかといった中身はこの層には出てこない。

---

## 1. 誰が計算を持つか — サーバー権威

**サーバーが唯一の権威。クライアントは入力と表示だけを担う。** 例外はない。

### 物理シミュレーションは存在しない

「コインプッシャー」という題材から素朴に考えると、
カードの山が押されて崩れる挙動を毎フレーム計算し、
それをどう同期するか（サーバー権威かクライアント予測か、ロールバックは要るか）という問題になる。

**この設計ではその問題は発生しない。**
`docs/spec.md` §4 のとおり、押し出しはダイス1個の出目と目標値の比較に抽象化してある。
連続的な物理量ではなく、1手番ごとの離散的な結果しかない。

| よくあるリアルタイム対戦 | PUSHER TABLE |
|---|---|
| 毎フレーム状態が変わる | 手番のアクションでしか状態が変わらない |
| 遅延が体感に直結する | 数百ミリ秒の遅延は問題にならない |
| クライアント予測とロールバックが要る | 要らない |
| 状態が大きいので差分同期が要る | 状態が小さいので毎回フルスナップショットでよい |

そのため、**クライアント予測もロールバックも実装しない。** 入れると裏向き情報の設計（§4）と真っ向からぶつかる。
クライアントが結果を予測するには山札とレーンの中身を知っていなければならないが、それは絶対に渡せない。

### 「動きのある画面」はどう作るか

リアルタイムに計算するのではなく、**結果先行・演出後追い**で作る。

1. クライアントが投入を送る
2. サーバーが判定し、「出目・成否・得点・横穴の有無」を返す
3. クライアントはその確定結果をもとに、ダイスが転がって止まり、カードが押し出されて落ちる演出を再生する

演出の長さはクライアントが決めてよい。サーバーはその間も待たない。
演出中に他プレイヤーの更新が届いたら、演出が終わってから反映する（クライアント側のキュー）。

この形にすると、ダイスの出目が演出の途中で変わることが原理的に起きない。
ネットワークの都合で「一度 6 と表示してから 3 に戻る」ような見え方をしない。

## 2. 通信方式 — HTTP で打ち、WebSocket で受け取る

**アクションは HTTP POST、更新の通知は WebSocket。** 双方向に何でも流すのではなく、役割を分ける。

```
  プレイヤーA                サーバー                プレイヤーB / 観戦者
     │                          │                          │
     │ POST /api/rooms/:code/turns/insert                   │
     ├─────────────────────────>│                          │
     │                          │ エンジンで判定・保存      │
     │<─────────────────────────┤                          │
     │  200 {room, result}      │                          │
     │                          │ room メッセージを配信      │
     │                          ├─────────────────────────>│
     │                          │      (WebSocket)         │
```

### なぜアクションを WebSocket に載せないか

- 既存の HTTP API がすでに認証・バリデーション・エラー形式・冪等性を持っている。同じものを WebSocket 上に作り直す理由がない
- 「アクションの成否」はリクエストへの応答として返るのが自然。WebSocket だと相関 ID を自前で管理することになる
- **WebSocket が使えない環境でも、ゲームが遊べる状態が保たれる。** 落ちるのは「即時反映」だけで、遊べなくはならない（§5）

### WebSocket が担うのは1つだけ

「あなた向けのルーム状態が更新された」を push すること。それ以外の責務を持たせない。

## 3. メッセージ形式

JSON。`t`（type）でタグ付けした判別可能なユニオン。
`v` はプロトコルバージョンで、互換性のない変更を入れるときに上げる。

### クライアント → サーバー

| `t` | 中身 | 意味 |
|---|---|---|
| `hello` | `{ v, code, token? }` | この接続をこのルームに紐づける。最初に必ず送る |
| `ping` | `{}` | 生存確認 |

`token` は参加時に発行したもの（`docs/spec.md` §8 / ルーム API と同じ）。
省略すると観戦者として扱い、裏向き情報を一切含まないビューを送る。

### サーバー → クライアント

| `t` | 中身 | 意味 |
|---|---|---|
| `welcome` | `{ v, code, playerId }` | `hello` を受理した。`playerId` は観戦者なら `null` |
| `room` | `{ rev, room }` | ルーム状態のスナップショット（**この接続向けにマスク済み**） |
| `error` | `{ code, message }` | `hello` が不正、ルームが無い、トークンが違う |
| `pong` | `{}` | `ping` への応答 |

`room` は HTTP の `GET /api/rooms/:code` と**同じ形**（`RoomView`）にする。
クライアントは受け取り口が2つあるだけで、扱う型は1つで済む。

### `rev` で順序を決める

HTTP のレスポンスと WebSocket の push は別経路なので、追い越しが起こりうる。
`rev`（サーバーが状態を更新した時刻から作る単調増加の整数）を必ず添え、
**クライアントは手元の `rev` 以下のスナップショットを捨てる。**

これで「自分の手番の結果を表示した直後に、1つ前の状態が届いて巻き戻る」が起きない。

### 部屋の作成と参加は HTTP のまま

WebSocket は購読するだけで、部屋を作ったり参加したりはしない。

| やること | 口 |
|---|---|
| 部屋を作る | `POST /api/rooms` |
| 参加する | `POST /api/rooms/:code/players` |
| 開始する | `POST /api/rooms/:code/start` |
| 更新を受け取る | WebSocket `hello` → `room` |

参加より先に WebSocket を繋いでも意味がないので、クライアントは
**トークンを得てから接続する**（観戦は例外で、トークンなしで繋ぐ）。

## 4. 裏向き情報 — 接続ごとに別のペイロード

このゲームは「レーンの中身と滞留エリアが裏向き」という情報設計が核にある（`docs/spec.md` §8）。
**マスク結果はプレイヤーごとに違う**（自分の手札は見えるが他人のは見えない）ため、
1つのルームへの配信であっても、**接続ごとに `viewFor(game, playerId)` を通した別々のメッセージを送る。**

「同じ JSON を全員にブロードキャストする」実装を絶対に作らない。
一度でも作ると、そこが裏向き情報の漏洩口になる。

### トークンはレジストリに置かない

接続レジストリ（§6）が持つのは `connectionId` と `roomCode` と `playerId` だけ。
**トークンは `hello` の検証に使うだけで保存しない。** 保存すると、接続の一覧を読めることが
「なりすませること」と同じ意味になってしまう。

## 5. 切断と再接続 — WebSocket は「速くする仕組み」であって前提ではない

### ポーリングは消さない

クライアントは常に `GET /api/rooms/:code` のポーリングを持ち続ける。WebSocket はその間隔を変えるだけ。

| WebSocket の状態 | ポーリング間隔 |
|---|---|
| 未接続 / 切断中 | 2 秒（現行と同じ） |
| 接続済み | 15 秒（取りこぼしの保険） |

こうすると「WebSocket が使えない環境ではポーリングにフォールバックする」が
**分岐ではなく自然な帰結**になる。フォールバック経路だけ動作確認が漏れる、という事故が起きない。

### 再接続

切断されたらクライアントが指数バックオフで繋ぎ直す。

- 待ち時間: 0.5s → 1s → 2s → 4s → 8s（上限）、それぞれに ±20% の揺らぎを足す
- 揺らぎを入れるのは、サーバーが再起動したときに全員が同時に殺到しないようにするため
- 再接続後は `hello` を送り直し、**差分ではなくフルスナップショットを受け取る**

状態が小さいので、差分の仕組みを持つ必要がない。
「再接続したのに状態がずれている」という最も厄介なバグの種を、最初から作らない。

### サーバー側から見た切断

切断は**ゲームの進行に影響しない**。

- 接続が切れてもプレイヤーはルームから抜けない。手番は止まったままそのプレイヤーを待つ
- 接続レジストリから該当の `connectionId` を消すだけ
- 同じプレイヤーが複数のタブから繋いでもよい（`connectionId` 単位で管理するので自然に扱える）

「切断したら CPU が代わりに打つ」といった処理は**このドキュメントの範囲外**にする。
先にタイムアウトのルールを決める必要があり（`docs/spec.md` に無い）、通信層だけでは決められない。

## 6. サーバー側の構造

配信の中身（誰に何を送るか）と、配信の手段（どうやって送るか）を分ける。
手段はローカル開発と本番で違うが、中身は同じものを使う。

```
backend/src/realtime/
  protocol.ts   — メッセージの型と、クライアントからのメッセージの検証
  registry.ts   — 接続レジストリ（connectionId ↔ roomCode / playerId）
  hub.ts        — 接続・メッセージ・切断の処理と、ルーム更新の配信
```

- `hub.ts` は `send(connectionId, payload)` を**引数で受け取る**。WebSocket にも API Gateway にも依存しない
- ゲームエンジン（`backend/src/game/`）と同じく、この3つは I/O を直接持たない
- 実際に送るアダプタだけが環境ごとに変わる

| 環境 | 接続の受け口 | `send` の実体 | レジストリ |
|---|---|---|---|
| ローカル開発 | Node の `ws` サーバー | ソケットへ直接 `send` | プロセス内の `Map` |
| 本番（予定） | API Gateway WebSocket API | `PostToConnection` | DynamoDB |

### 配信のきっかけ

状態を書いたところが、そのまま配信する。ルーム API のハンドラが保存の直後に `publish(room)` を呼ぶ。
別プロセスの監視やポーリングを挟まない。

配信に失敗しても**アクションは成功扱いにする**。
更新の通知が届かなかったとしても、ポーリング（§5）が拾うため。
通知の失敗でプレイヤーの手番を巻き戻すほうが、はるかに悪い。

## 7. 本番（API Gateway WebSocket API）への展開

ローカルで動く形が先にあり、本番はそのアダプタを差し替える。**本番化は #15 では行わない。**

理由: 接続レジストリを Lambda 間で共有するには DynamoDB が要るが、
ルーム本体の保存がまだインメモリ（`backend/src/room/store.ts`）で、テーブルが1つも無い。
接続だけ先に DynamoDB へ載せても、ルーム状態が Lambda ごとにばらつく以上、意味がない。

**ルームの保存を DynamoDB にする作業と同じ単位で行う。** そのとき必要になるのは:

- `aws_apigatewayv2_api`（`protocol_type = "WEBSOCKET"`）と `$connect` / `$disconnect` / `$default` ルート
- 接続テーブル: `PK = CONN#<connectionId>` / ルームからの逆引き GSI（`ROOM#<code>`）、TTL つき
- Lambda に `execute-api:ManageConnections` の権限
- `PostToConnection` が `410 Gone` を返したらレジストリから消す（切断イベントの取りこぼし対策）

---

## 8. 決めたこと・決めていないこと

### 決めたこと

- サーバー権威。クライアント予測もロールバックも行わない
- アクションは HTTP、更新の通知は WebSocket
- 状態は毎回フルスナップショット。差分同期はしない
- 配信は接続ごとに個別のペイロード。全員へ同じ JSON を流さない
- ポーリングは常時持ち、WebSocket は間隔を変えるだけ
- 切断はゲームの進行に影響しない

### 決めていないこと

- 手番のタイムアウト（誰かが戻ってこないときの扱い）。ルール側の決定が先
- 観戦者の上限
- チャットや定型メッセージ。必要になったら `t` を足す
