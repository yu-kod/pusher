# 保存先の設計 — DynamoDB 単一テーブル（#78）

ルームの状態をどこに置くかを決める。ルールは `docs/spec.md`、通信は `docs/realtime.md` にある。
ここはその外側——**状態がどこに残り、同時に書かれたらどうなるか**——だけを扱う。

---

## 1. なぜ要るか

Lambda はリクエストごとに別の実行環境へ振られうる。
保存先がプロセス内のメモリだと、ルームを作った直後の参加で「ルームが無い」になったり、
2人が別々の状態を見たりする。**コンテナが再利用されている間だけたまたま動く。**

保存先を外に出さないかぎり、リアルタイム同期も結果画面も本番で確かめられない。

## 2. テーブル設計

**単一テーブル。** エンティティが少なく（ルームと接続の2つ）、
アクセスパターンもキー1つで引けるものしかない。

| 項目 | PK | SK | GSI1PK | GSI1SK | TTL |
|---|---|---|---|---|---|
| ルーム | `ROOM#<code>` | `ROOM` | — | — | `expiresAt` |
| 接続（#90） | `CONN#<connectionId>` | `CONN` | `ROOM#<code>` | `CONN#<id>` | `expiresAt` |

アクセスパターンはこれだけ。

- ルームコードで1件読む → `GetItem`（整合性のある読み取り）
- ルームを作る / 更新する → 条件付き `PutItem`
- 接続 ID から所属ルームを引く → `GetItem`
- ルームに繋いでいる接続を全部引く → GSI1 を `Query`

GSI1 は `GSI1PK` を持つ項目しか載らない（スパースインデックス）ので、
ルームの書き込みに索引の費用は乗らない。Scan は使わない。

GSI1 には `playerId` も載せる（`projection_type = "INCLUDE"`）。配信は接続ごとに
マスク済みの別ペイロードを作るので、逆引きした時点で「その接続が誰向けか」が
分からないと、接続の数だけ読み直すことになる（`docs/realtime.md` §4）。

**ルームの状態は属性に分解せず、直列化した JSON を `body` に1つ置く。**
`Balance.pushCount` が関数で、素朴な JSON 化では黙って消えるため、
保存と復元は `backend/src/room/serialize.ts` を必ず通す（詳細はそのファイルの冒頭）。

## 3. 同時更新 — 版（rev）による条件付き書き込み

API は「読む → エンジンで解決する → 書く」を素で行う。
2人が同時に叩くと、後の書き込みが前の結果を踏み潰す（lost update）。

項目に `rev` を持たせ、**読んだときの版を条件にして書く。**

- 作成: `attribute_not_exists(PK)` — ルームコードの衝突を弾く
- 更新: `rev = :expectedRev` — 先に別の更新が入っていたら弾く

条件が外れたら `RoomConflictError` を投げ、API は **409** に変換する。
クライアントは状態を取り直してやり直す。

版に `updatedAt` を使わないのは、同じミリ秒に2つの書き込みが重なると条件をすり抜けるため。
1つずつ増える数を持たせる。

サーバー側での自動リトライは**入れていない**。手番制のいま同時に届くのはロビーの参加くらいで、
リトライは「読み直して解決し直す」ことになり、どの結果を採るかがルールの判断になる。
同時投入を入れる（#80）ときに、`docs/realtime.md` §8 のとおりここへ足す。

## 4. TTL

`expiresAt`（epoch 秒）に載せる。ルームは最終更新から 24 時間で消える
（`backend/src/room/dynamo-store.ts` の `ROOM_TTL_SECONDS`）。接続は 2 時間
（`backend/src/realtime/dynamo-registry.ts`）。API Gateway の接続自体が最長2時間なので、
それより長く持っていても意味がない。
アカウントの無いサービスなので、遊び終わった卓を溜め込まない。

## 5. 切り替え

環境変数 `APP_TABLE_NAME` があれば DynamoDB、無ければインメモリ
（`backend/src/room/create-store.ts`）。Terraform が Lambda に渡す。
**ローカル開発と結合テストは環境変数を置かないのでインメモリのまま動く。**

保存先は `RoomStore` インターフェースの背後にあり、API はそれだけに依存する。

## 6. 決めていないこと

- 終わったゲームの記録（統計・結果画面）。別のプレフィックスで同じテーブルに載る想定
- バックアップ（PITR）。TTL で消える前提のデータなので、いまは取らない
