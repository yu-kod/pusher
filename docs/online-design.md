# オンライン対戦の設計提案 — 進行方式・駆け引き・プレイ時間

`docs/spec.md` v0.2 は**卓上のボードゲーム**として設計され、シミュレーション7回でバランスの目標値をすべて達成している。一方このプロジェクトの目標は「Web上でアプリらしい動きのある画面でオンラインリアルタイムに遊べること」。

この2つのあいだには、**ルール側で決めないと埋まらない差**が3つある。この文書はその差を数値で示し、進行方式の案を3つ比較して1案を推す。

数値はすべて `npm run sim`（既定値・期待値戦略・2000ゲーム・seed 11）で実測した。

---

## 0. 結論

**本命：ティック同時進行制 ＋ ボール ＋ 先行権。** 3つはセットで効く。

| 要素 | 解決する問題 |
|---|---|
| **ティック同時進行** — 全員が同時に投入し、各自が自分のタイミングで降りる | 待ち時間が全体の75%を占める（§1-1） |
| **ボール** — レーンの中で位置が見える大物トークン | 共有台に取り合いがない（§1-2） |
| **先行権** — 早く降りた人ほど次ラウンドで先に解決する | 降りる判断に報酬がない／席順の偏り |

v0.2 のルール本体（投入 → 目標値 → d6 → 押し込み → 落下、横穴＝バースト、未確定得点、ジャックポット）は**変えない**。変えるのは「誰がいつ打つか」だけである。

代案は §5（手番制のまま高速化）と §6（完全リアルタイム）。

## 1. いま何が足りないか

### 1-1. 待ち時間が全体の4分の3を占める

| 指標（4人） | 実測 |
|---|---|
| 1ゲームの投入ラウンド総数 | **136.4 回** |
| 1手番の投入ラウンド数 | 平均 2.62 回（中央 2 / p90 5 / 最大 11） |
| 1ラウンドでいちばん長い手番 | 平均 4.06 回（p90 6） |

手番制では、この 136.4 回を**1つずつ順番に**解決する。1回の解決を「判断5秒＋ダイスと落下の演出8秒＝13秒」とすると **約30分**、うち自分が動いているのは 136.4 ÷ 4 = 34.1 回ぶんの **約7分** で、**残り22分（75%）は他人を見ている時間**になる。

卓上ならこの時間は会話で埋まる。オンラインでは埋まらない。「アプリらしい動きのある画面」で22分待たされるのは、動きがあるぶんかえって苦しい。

`docs/design-notes.md` §4 はこれを「⚠️ 1手番が長い」として挙げ、改善案に同時手番を示しつつ、再設計が必要な3点（同じレーンに複数人が投入した場合の処理順／投入口増設の追加手番／横穴を出したプレイヤーの記録）を未解決のまま残している。本文書 §4 でこの3点に答える。

### 1-2. 台を共有しているのに、他人の手が自分の盤面をほぼ変えない

spec は「プッシャー台を全員で共有することで、ソロ体験であるメダルゲームを多人数の駆け引きに変換する」を設計の核に掲げている。しかし**現在のルールでは、他人の押し出しが自分の盤面をほとんど動かさない。**

押し出し1回でレーンがどう変わるかを数えると：

| 結果 | 滞留枚数の変化 | レーンの厚み（奥の山）の変化 |
|---|---|---|
| 失敗 | **+1**（投入カードが残る） | 0 |
| 成功（1・2コイン札、押し込み1枚） | +1 −1 = **±0** | 0（押し込み枚数＝落下枚数） |
| 成功（3コイン札、押し込み2枚） | +1 −2 = **−1** | 0 |
| 横穴 | 成功と同じ | 0 |

つまり他人が1回押しても、そのレーンの目標値は **±1 しか動かず、しかも失敗されると自分に有利になる**。レーンの中身は §4-3 のとおり増えも減りもしない。

**取り合いになる要素がない。** 誰かに先を越されて損をする構造がないので、「あのレーンは熟しているから先に取られる前に行く」という判断が生まれない。他人の手番は、自分にとって（わずかに有利な）環境ノイズでしかない。

現在ひとつだけ競合しているのは**ジャックポット**（カウンター5到達後、先に6を出した人がプールを総取り）だが、誰が横穴を出すかは運でしかなく、狙って競る対象にならない。`docs/design-notes.md` §2 が「得点経路が1本しかない」として挙げている問題と、根は同じである。

**同時進行にするだけではこれは直らない。** 同時に打っても取り合う対象がなければ、全員が並んでソロプレイをするだけになる。§4 でボールをセットにする理由がここにある。

### 1-3. 「投入カードを覚える」がオンラインでは成立しない

spec §7 の未決定事項に、こうある。

> 投入カードを **表向きで置いてから判定 → 裏返す** 手順は、他プレイヤーに「何を投入したか」を一瞬見せることになる。これを記憶するカウンティング要素を残すか（中略）未決定

**オンラインでは「残すか」を選べない。** クライアントは全履歴を保持できるし、手でメモを取るプレイヤーと取らないプレイヤーのあいだに不公平が生まれる。隠しても、片方だけが数えられる状態になるだけである。

決めるべきはこうなる。§8 で回答する。

## 2. 守るもの／変えてよいもの

シミュレーション7回で積み上げた結論を壊さないために、線を引いておく。

**守る（変えない）**

- 解決手順そのもの：投入 → 目標値（コイン数＋滞留枚数）→ d6 → 押し込み → 落下 → めくる
- 横穴＝バースト、未確定得点、ジャックポット（§5 の構造）
- デッキ構成90枚、押し込み枚数「コイン数÷2 切り上げ」、初期滞留9枚、ドロー3枚、13ラウンド
- 勝利条件：13ラウンド後の最多得点（§7 で再確認する）
- ゲームエンジンは純粋関数、乱数は `Rng` を引数で注入（CLAUDE.md）

**変えてよい**

- 誰がいつ打つか（手番制であること自体）
- スタートプレイヤーをラウンドごとに交代させる仕組み（§4 の先行権が置き換える）
- 「投入口増設」の追加手番の扱い（同時進行では意味が変わる）
- 情報の見せ方（§8）

## 3. 本命案の全体像

**ラウンドを「ティック」の連続にする。1ティックで、まだ降りていない全員が同時に1投入ラウンドを行う。**

```
ラウンド開始（全員が参加中）
  ├ ティック1: 全員が同時に宣言 → 先行権順に解決 → 各自が「続ける／降りる」を選ぶ
  ├ ティック2: 降りていない人だけが宣言 → 解決 → 選ぶ
  ├ ...
  └ 全員が降りた（または手札切れ・横穴）→ ラウンド終了。ドロー3枚
```

ラウンド数は13のまま。ゲーム終了条件も変えない。

---

## 4. 本命案の詳細

### 4-1. ティックの進行

1. **宣言（同時・非公開）** — 参加中の全員が、レーン1つと手札1枚を選ぶ。制限時間は12秒を目安とする。時間切れ・切断は「降りる」として扱う
2. **解決（先行権順）** — 宣言した人を先行権の順に1人ずつ解決する。目標値は**その人の解決の直前**の滞留枚数で算出する
3. **押し引き** — 解決が終わったら、各自が未確定得点を見て「次のティックも入るか、ここで降りるか」を決める。降りた人は未確定得点を確定し、そのラウンドは以後不参加

横穴を踏んだ人はその場でラウンドから抜ける（未確定得点はジャックポットへ）。手札が尽きた人も抜ける。

**「投入口増設」の追加手番**（§6）は、同時進行では「そのティックでもう1枚投入できる」に読み替える。追加手番という概念が消えるため、解決も単純になる。

**横穴を出したプレイヤーの記録**は不要になる。ゲーム終了時の未払い出しジャックポットは §5 のとおり流すので、誰が最後に横穴を出したかを覚えておく必要がもともとない（#68 で解決済み）。

### 4-2. 先行権

**前のラウンドで早く降りた順が、次のラウンドの解決順になる。**

- 同じティックで降りた人どうしは、前ラウンドの先行権の順
- 初回は席順
- 横穴や手札切れで「降りさせられた」人は、自分から降りた人より後ろ

これにより **spec §3 の「スタートプレイヤーをラウンドごとに左隣へ移す」は不要になる。** 順番は席で決まるものから、**プレイヤーが点を諦めて買うもの**に変わる。手番順ごとの勝率の偏り（現在 0.026）は、構造ごと消える。

### 4-3. ボール（大物トークン）

spec §9 の「ボール（大物トークン）」を、本命案の必須要素として採る。

- 各レーンの奥の山に **1個ずつ**、位置が見えるトークンを混ぜる。**あと何枚押し込めば落ちるかが全員に分かる**
- 落ちたら大きな点（**10点**を初期値とする。1手番の取り分 6.25点の約1.6倍）。未確定得点に入るので、横穴を踏めば失う
- 落ちたら、そのレーンの奥に新しいボールを入れる（位置は一定の距離をとる）

**ボールが §1-2 を直接解決する。** レーンの中身は裏向きのままなので「何が落ちるか分からない」快感（§4-2）は残るが、**ボールの位置だけは公開情報**になる。すると：

- あと1枚で落ちるレーンは、全員が狙う
- 同じティックにそのレーンへ集まったら、**先に解決する人が取る**
- だから先行権に値段がつき、**早く降りること（＝点を諦めること）が報われる**

3つの要素がここで噛み合う。同時進行が「取り合いが起きる状況」を作り、ボールが「取り合う対象」を置き、先行権が「取り合いの勝敗をプレイヤーの判断で決める」。どれが欠けても残りが空回りする。

`docs/design-notes.md` §2（得点経路が1本しかない）と §3（トランプとサイコロで代用できてしまう＝専用コンポーネントがない）にも、ボールは同時に効く。

### 4-4. プレイ時間

同時進行でも**解決の総数は減らない**（136.4回は必ず起きる）。減るのは**待ち時間**であり、短縮は並行化から来る。

| | 投入R総数 | 解決の並び | 実時間の試算 | 待ち時間の割合 |
|---|---|---|---|---|
| 4人・手番制（現行） | 136.4 | 逐次 136.4 回 | 約30分 | **75%** |
| 4人・同時進行 | 136.4 | **52.8 ティック** | 16〜23分 | **35%** |
| 3人・手番制（現行） | 104.3 | 逐次 104.3 回 | 約23分 | 67% |
| 3人・同時進行 | 104.3 | **49.6 ティック** | 15〜21分 | 30% |

- ティック数は「ラウンドでいちばん長い手番」×13で求めた（4人 4.06 / 3人 3.81、実測）
- 手番制は1解決13秒、同時進行は1ティック18〜26秒で試算した。**幅は演出の設計で決まる** — 4人ぶんの落下を順に見せると26秒、レーンごとにまとめて同時に見せると18秒
- 待ち時間の割合は、同時進行では「参加している平均ティック数 2.62 ÷ ラウンドの長さ 4.06」から算出

**3人では圧縮率が下がる**（2.1倍、4人は2.6倍）。人数が多いほど同時進行の利きが大きい。

目標は **1ゲーム15〜20分**。オンラインで「もう1回」と言える長さであり、1ゲーム40〜60分という現在の想定（卓上前提）の1/3である。

### 4-5. 再検証が必要なこと

進行方式を変えれば、達成済みの数値はいったん無効になる。既存の sim ハーネスで測り直す。

1. **滞留の厚み**（目標 3〜5枚）— 1ティックで最大4枚投入されるので厚くなりやすい。初期滞留9枚を下げる必要が出る可能性が高い
2. **1手番（＝1ラウンドの参加ティック数）**（目標 2〜4回）
3. **自分でやめた割合**（目標 0.3 以上）— 先行権という報酬がつくので、早く降りすぎる方向に振れないか
4. **手番順ごとの勝率**（目標 差 0.05 以内）— 先行権が特定のプレイヤーに固定されないか。「初回の席順」がどこまで尾を引くか
5. **新指標：同一レーンへの集中率** — 取り合いが実際に起きているかを測る。1ティックで同じレーンに2人以上が入った割合。これが0に近いなら、ボールを足しても取り合いは生まれていない
6. **ボールの点数10点が強すぎないか** — ボール獲得者の勝率

エンジンは純粋関数なので、ティック解決を足せば既存の指標はそのまま出る。5 だけ新規に足す。

## 5. 代案A：手番制のまま高速化する

ルールは v0.2 のまま、制限時間と演出の速度、観戦の見せ方だけを変える。

- 1投入ラウンドの解決を 13秒 → 7秒 に詰めれば、136.4 × 7 ＝ **約16分**
- 他人の手番中、自分が「次に狙うレーン」を先に予約できるようにして、待ちを準備時間に変える

**利点**

- 検証済みの数値がそのまま生きる。シミュレーション7回の成果を一切捨てない
- 実装は #15（WebSocket による状態同期）の素直な延長で済む
- 最短で「遊べる状態」に到達する

**欠点**

- **待ち時間の割合は75%のまま。** 短くはなるが、構造は変わらない。人数が増えるほど悪化する
- §1-2（取り合いがない）と §1-3（記憶要素）は解決しない
- 演出を詰めるほど「アプリらしい動き」とは逆方向に進む。落下のめくりは本作の快感の中心（§4-2）なので、ここを削ると面白さを削ることになる

**向いている場面**：まず動くものを出して手触りを確かめたい段階。本命案への踏み台として無駄にならない（同時進行は手番制の解決関数を並べたものなので、実装が積み上がる）。

## 6. 代案B：完全リアルタイム（先着順・クールダウン制）

ティックを廃止し、各自が任意のタイミングで投入する。投入後は個別のクールダウン（例：3秒）が入る。

**利点**

- 「アプリらしい動き」は最大。実機のプッシャー台にいちばん近い
- ダウンタイムは完全に消える
- ボールの取り合いがそのまま**反射の勝負**になり、盛り上がりは分かりやすい

**欠点**

- **期待値の計算が反射神経に負ける。** spec 冒頭の「プレイヤーが考えるのは期待値と、どこで引くかの2点」という設計の核と正面から衝突する
- **通信遅延がそのまま有利不利になる。** 同じレーンへの同着をどちらが取るかがネットワーク品質で決まる
- 押し引きの「ここで降りる」を考える間がない。チキンレースが成立しなくなる恐れが大きい（#67 で苦労して成立させた部分）
- サーバー権威の実装が最も重い（全アクションのタイムスタンプ順序付け、ラグ補正）

**判断**：カジュアルなパーティゲームとしては成立しうるが、本作が積み上げてきた設計からは外れる。採らない。

## 7. 勝利条件

**現行のまま変えない。** 13ラウンド後の最多得点、同点なら手札が多いほう、それも並べば引き分け。

オンライン向けに検討した代案と、採らない理由：

| 案 | 内容 | 判断 |
|---|---|---|
| 目標点先取 | 先に100点に到達した人の勝ち | **採らない。** 終盤は盛り上がるが、1ゲームの長さが読めなくなる。オンラインのマッチングでは「だいたい何分で終わるか」が確約できることの価値が高い |
| 3戦マッチ | 短い1戦を3回、合計点で決める | **保留。** 1戦15〜20分の本命案とは相性がよく、逆転の余地も増える。ただし総プレイ時間は45〜60分に戻る。1戦の形が固まってから考える |
| 現行維持 | 13ラウンド後の最多得点 | **採る** |

**「最後まで逆転の芽がある」はボールとジャックポットが担う。** ボール10点は1手番の取り分（6.25点）の1.6倍で、最終ラウンドでも順位をひっくり返しうる。勝利条件そのものを変える必要は薄い。

## 8. 情報の扱い — §1-3 への回答

**滞留エリアに投入されたカードの内訳は、UI で全員に見せる。**

- **隠す選択は取れない。** クライアントは履歴を保持できるので、隠しても「数えられる人だけが有利」になるだけ。不公平を実装するに等しい
- **見せても壊れない。** レーンの奥の山（stock）は最初から誰も中身を知らないままなので、「何が落ちるか分からない」快感（§4-2）は残る。分かるようになるのは「これから押し込まれる滞留カードが何だったか」だけ
- 目標値の計算に必要な情報（滞留の**枚数**）はもともと公開情報であり、内訳が加わっても判断の種類は増えるが情報の非対称は生まれない

これは spec §7 未決定事項の「カウンティング要素を残すか」に対する**オンライン版としての回答**であり、物理版とは別の結論になってよい。物理版は「一瞬見せて裏返す」を維持すればよい。

なお CLAUDE.md の「裏向き情報をクライアントへ返さない」は引き続き守る。**表向きにすると決めたものだけを返す**のであって、裏向きのまま返すのではない。奥の山の中身とほかプレイヤーの手札は、これまでどおり返さない。

## 9. コイン以外の要素を足す順序

spec §9 は「同時に足すと何が効いたのか分からなくなる」としている。計測のために段階を分ける。

| 段階 | 足すもの | 測ること |
|---|---|---|
| 1 | ティック同時進行（進行方式のみ） | §4-5 の 1〜4。v0.2 の達成値がどこまで保てるか |
| 2 | 先行権 | 自分でやめた割合、手番順ごとの勝率 |
| 3 | ボール | 同一レーンへの集中率（新指標）、ボール獲得者の勝率 |
| 4 以降 | フィーバー／チャッカー／ダブルアップ（§9） | 都度 |

**ただし 1〜3 はひとつの設計として扱う。** 段階を分けるのは計測のためであって、1 だけで止めると §1-2（取り合いがない）が残ったままになる。「1 を入れて数値が悪化したから戻す」という判断は、3 まで入れてから下す。

「横穴を左右レーン限定にする」（§9）は、同時進行では**中央レーンに全員が集まる**という新しい問題を生むので、いったん見送る。

## 10. 実装への影響

### エンジン

現在の `GameState`（`backend/src/game/setup.ts`）は、手番が1つしかない前提で作られている。

| 現在 | 同時進行では |
|---|---|
| `pendingPoints: number`（ゲームに1つ） | `Player.pendingPoints` へ移す |
| `currentPlayerIndex: number` | 解決順のキュー（先行権）＋「このラウンドでまだ降りていない人」の集合 |
| `insertionRoundsThisTurn` | ラウンド内のティック番号 |

**既存の `resolveInsertionRound`（`round.ts`）は1人ぶんの解決としてそのまま使える。** その上に「1ティック＝宣言の配列を先行権順に畳み込む」関数を足す形になる。エンジンは純粋関数のままにでき、`Rng` の注入も変わらない。

### サーバー

同時進行はサーバー側に**締め切り**という新しい責務を持ち込む。

- 宣言の締め切りをサーバーが持つ（クライアントのタイマーは表示のみ）
- 締め切りまでの宣言は**非公開**で、締め切り後にまとめて公開する
- 未宣言・切断は「降りる」として扱う

### 決めるなら今がいちばん安い

**#15（WebSocket による状態同期）はまだ未着手である。** 手番制を前提に同期を実装したあとで同時進行へ移ると、上の3点がすべて後付けになる。特に「非公開の宣言を締め切りまで保持する」はプロトコルの形そのものに関わるので、後から差し込むのは高くつく。
